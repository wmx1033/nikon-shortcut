# 尼康相框水印优化建议

依据 `尼康相框水印-脚本.sh`（v1.0.0）的阅读结论整理。优先级按影响面排序：先处理会画错、丢信息或误跳过的问题，再处理批量时能感觉到的耗时，然后是使用体验，最后是仓库维护。P0 已写入脚本。

快捷指令仍以单文件分发。下面的建议都在这个前提下成立。

## 总览

| 优先级 | 类别 | 条目 | 做完之后 |
| --- | --- | --- | --- |
| P0 | 成片正确性 | 4 | 缺元数据的照片不再被画成尼康；注释和水印标记不再互相覆盖；转色域后的标签与像素一致；原片不会因文件名被误跳过 |
| P1 | 批量速度与地点 | 3 | 重复运行不再每次编译；同一批照片不再反复解码 logo、反复反查同一地点 |
| P2 | 使用体验 | 3 | 失败能看出来；一张坏图不会终止整批；参数文字更接近机身回放 |
| P3 | 工程维护 | 2 | 脚本和 `assets/` 共用一套图；快门、品牌、色域、文件名可以单独验证 |

## P0 成片正确性

已在 `尼康相框水印-脚本.sh` 落地。下面保留问题本身，并记下现在的做法。

### 1. 缺少机身型号时被画成尼康

`Model` 缺失时曾经默认写成 `"Nikon"`，于是没有机身信息、或其他品牌但缺型号的照片会被画上尼康标。

现在型号缺失时是空字符串。只有 `Make` 含 `NIKON`，或真实型号以 `NIKON` 开头，才画尼康标。

### 2. 水印标记覆盖原来的注释，防重复也不稳

标记曾经整段替换 `UserComment`，读取时还要求整段相等。带字符集前缀时认不出，改名后会再加一层框。

现在原注释保留，标记追加在末尾。读取时认标记片段，并识别 EXIF 的 `ASCII` / `UNICODE` / `JIS` 前缀。解不开的二进制注释保持原样。已经写成纯标记 `NIKON-WATERMARK` 的旧成片仍会跳过。

### 3. 转成 sRGB 后，颜色标签可能仍是原来的工作色域

Adobe RGB、ProPhoto RGB、Wide Gamut RGB 仍画进 sRGB。转换时会清掉输出 metadata 里的 `ICCProfile`，让成片按画布的 sRGB 写配置。sRGB 与 Display P3 仍沿用原来的色彩空间和 ICC。

### 4. 文件名里出现「-相框」就会跳过

以前文件名主干只要包含 `-相框` 就跳过，`旅行-相框素材.jpg` 这类原片不会被处理。

现在只认结尾的 `-相框` 和 `-相框-2` 这种形态。EXIF 标记继续做第二道。

## P1 批量速度与地点

单张照片的主要时间在解码和编码。下面三项在一批图、或反复运行时才明显。

### 1. 每次运行都现场编译整份脚本

脚本约 440KB，其中绝大部分是 logo 的 base64。`/usr/bin/swift -` 每次都编译这份源码，也就是 README 里写的约 1–3 秒启动开销。

单文件可以保留。按脚本内容做哈希，第一次编译到 `~/Library/Caches`，之后直接执行那个二进制。脚本一改，哈希变了，缓存自然失效。

### 2. 每张照片都重新解码同一批 logo

`brands` 表和 `drawMark` 都在逐张循环里。`drawMark` 对传入的 base64 现场解码并建 `CGImage`。尼康大标一份约 108KB，一批图会重复解同样的标。

建议：品牌表和已解码图像放到循环外，按标的内容缓存 `CGImage`。一张照片只解码它真正要用的那几枚。

### 3. 地点反查又慢又容易整行留空

`locationCaption` 有三处叠在一起：

- 缓存键是完整经纬度。同一景点连拍几乎不会命中。地名只到城市，四舍五入到约 1 公里就够。
- 只缓存成功结果。离线、超时、没有城市名的点，每张都再等最多 3 秒。
- 城市名里只要有一个非拉丁字符，整段说明被丢弃，国家名也不显示。城市不是拉丁字母时，至少保留国家，或退到省、州。

`CLGeocoder` 在较新的 macOS 上已被标记弃用，当前仍能用。等它真正影响运行时再迁到 MapKit 即可，不必和上面三处绑在一起做。

位置：`locationCaption`。

## P2 使用体验

### 1. 整批失败时快捷指令仍显示成功

单张失败被吞掉，只往标准错误写「跳过」。全部失败时进程仍以 0 退出。快捷指令没有汇总，用户只能自己对输出文件。

建议：结束时输出一行结果，写明处理、跳过、失败各几张。存在失败时返回非 0。

### 2. 一枚标解码失败会终止整批

`drawMark` 对 base64、图像源和 `CGImage` 使用强制解包。这里抛出的是致命错误，外层 `catch` 接不住，后面的照片不会再处理。

建议：解码失败时跳过这一枚标，或跳过这一张照片并计入失败，让循环继续。

### 3. 光圈和焦距的写法可以更接近机身

快门已经吸附到标准档。光圈仍是 EXIF 有理数直接转成字符串，可能出现 `f/1.799999` 这类值。可以用同一套吸附。

DX 机身（例如 Z30）现在写的是物理焦距。若希望和机身回放一致，可以并列 35mm 等效焦距。这是展示选择，不影响正确性。

## P3 工程维护

### 1. 脚本内嵌图和 `assets/` 是两份资源

十二个镜头品牌、三张机身标、两张尼康标都嵌在脚本里。`assets/` 里又有一套供 README 展示的图。Z6 II 已经分叉：脚本里是 1240×149 的 JPEG，绘制时若宽度恰好为 1240 就裁成 372×149；`assets/camera-z6ii.jpg` 已经是裁好的 372×149。以后换一张同样宽度的标，会被误裁。

建议：以 `assets/` 为唯一来源，裁切做在素材上，删掉按宽度 1240 裁剪的特判。用一个小脚本把图片嵌进可分发的单文件。仓库里给人看的是 Swift 源码和图片，快捷指令里仍是现在这一份脚本。

### 2. 纯逻辑现在无法单独验证

快门格式化、品牌匹配、色域选择、输出文件名、跳过规则都写在 AppKit 绘制流程里。改一处只能靠导入快捷指令试。

源码从脚本里拆开之后，这几段可以不启动图形环境就验证。批量试跑仍需要 macOS。

## 建议落地顺序

1. P0 的四项。已落地：判断和 metadata 已改，版式未改。
2. P1 的 logo 缓存，以及地点缓存、失败缓存、非拉丁城市的退路。这三处都在现有脚本里。
3. P1 的编译缓存。它改变启动方式，适合单独做，并确认快捷指令的权限和路径仍正常。
4. P2 的退出码与汇总、`drawMark` 的失败处理。
5. P3。把资源收成一份，并给纯逻辑补上可重复运行的检查。光圈吸附和等效焦距可以跟版式一起看。

## 可以保持现状

- 单文件 `.shortcut` 只放在 Releases，仓库不存放导入包。
- 白边和底部信息栏的比例、JPEG 质量 0.96。
- 快门吸附标准档。
- sRGB、Display P3 原样保留；工作色域转为 sRGB。P0 只补「转换之后的标签」。
- 照片一张一张处理。全尺寸位图的内存占用已经按单张计算，并行解码会把峰值内存乘上去。
- 无 GPS 或离线时地点行留空、不中断整批。
